# Cloud revision controller

The controller accepts signed GitHub `push` and `pull_request` deliveries for one enrolled repository and its allowlisted target branches. It records each accepted delivery before acknowledging it, publishes a pending commit status for the event's SHA, and keeps a durable SHA-keyed job until the final status is published. The worker retries interrupted or unpublished jobs. A repeated delivery or a push and PR event for the same SHA and enrollment share one job.

Install `scripts/cloud-revision.py` as trusted controller code. Create a private enrollment JSON from `scripts/cloud-revision/enrollment.example.json`, with mode `0600`, and set `stateDirectory` to a controller-owned directory with mode `0700`. The example uses placeholders. `snapshotRoot` must be inside the enrolled workspace roots used by `infinite-check`; the installed launcher, runner alias, origin and workspace must already be enrolled there. Pin `profileSha256` to the approved `scripts/cloud-check/linux-runner.json` digest. Set `mode` to `npm` with `command` exactly `npm run check` for standard locked `npm ci` checks, `compose` with an empty command for an enrolled `.infinite/check.json` recipe, or `command` with the operator-owned argv passed to `infinite-check --project-command`. The target repository cannot replace the launcher or its enrolled command. The controller pins the installed launcher's file digest on first start and refuses changed enrollment in an existing state directory. A launcher, command, profile, runner or target change needs a new status context and state directory so earlier statuses cannot be reused.

Store `webhookSecretFile` and `githubTokenFile` as separate mode `0600` files. The bearer token needs permission to create repository commit statuses. The publisher uses GitHub's REST commit-status endpoint at `https://api.github.com` by default; pass `--api API_BASE` to both service commands for a different GitHub API base. Configure the GitHub webhook to send `push` and `pull_request` events, use the same secret, and forward `POST /github-webhook` through a TLS reverse proxy to `127.0.0.1:8418`. The controller verifies the HMAC, repository, base branch and head SHA. It rejects fork heads and deliveries for other repositories or branches. Never expose the loopback listener directly to the network.

Install the service and timer examples under the host's systemd configuration and adapt only the generic install locations and service account to the owner-operated controller host. The receiver stays up for webhook ingress; the timer runs `--once` every 30 seconds. Test the receiver and worker with a disposable enrolled repository and a fake status API before enabling real webhook delivery. Do not enable branch protection until the owner approves the repository-specific rule.

Each run fetches the event SHA from the configured origin into a temporary clean checkout under `snapshotRoot`. Git system/global configuration and checkout hooks are disabled during capture, and the controller never executes target checkout code. Only the configured launcher command is dispatched to the enrolled guest. The check's own cloud receipt remains the source for runner and toolchain evidence; the controller records its exit, output digest, source SHA, command/profile enrollment digest and status publication outcome in its private state. A later SHA receives its own pending status and cannot inherit an earlier pass.
