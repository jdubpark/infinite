# Agent runtimes and accountable autonomous work

**Implementation update, November 24, 2026.** A local Infinite branch now exposes resumable mission progress, requires new goal plans to identify which pinned criteria their tasks advance, and holds automatic merges when the checked commit lacks independent model-family review. In a controlled child failure, the observer saw the worker exit and the scheduler started exactly one recovery planner. The cross-repository comparison below describes the research baselines. [Pilot evidence and limits](operations.md#implementation-pilot).

**Pilot a resumable child-progress feed on one Infinite mission, including the case where the child disappears.** Paseo remembers which parent asked to hear from a child. Herdr tells an observer when it has missed events. Combine those two ideas so a returning coordinator can find an assigned child's latest report and check result. If the child becomes unreachable, the host must distinguish a lost observer from a dead or fenced worker before assigning replacement work. Measure recovery time and polling cost together.

Two prerequisites matter more than increasing worker count. Infinite's checked-in launch fuse counts starts. Its spend display can show incomplete costs. Its delivery path checks a reviewed head, but the inspected gate does not establish independent review across every contributing model family. Close those gaps before expanding automatic delivery or metered fan-out.

The three source studies trace normal operation and failure. A second research pass checks specific operational claims against current main and resolves four design decisions. [Herdr](herdr.md) · [Paseo](paseo.md) · [Infinite](infinite.md) · [Operational findings and design decisions](operations.md).

## What happens to one assignment

| Question | Herdr | Paseo | Infinite |
| --- | --- | --- | --- |
| Who owns the work? | A runtime owns a workspace, tab, and terminal pane. It recognizes the CLI agent occupying it. | A daemon owns a managed agent, workspace and parent relationship. A provider owns the native conversation. | A goal or mission owns approved work. A team owns tasks and revisions. Each member attempt is bound to a session and a role. |
| How does a child start? | A caller starts a CLI in a ready shell pane, sends terminal input and can wait on observed status. | Agent tools create a child asynchronously or send a typed message. A caller can request a finish notification. Keyed creation and direct-message RPCs have separate receipt contracts. | A host validates a coordinator's plan, persists the launch identity, selects an eligible profile, and starts a detached worker. Task dependencies become eligible after integration. |
| What does a reply establish? | The pane settled or produced output. If it was already working, the wait can match an earlier turn. | A lifecycle transition or dispatch acknowledgement. A permission request, unreachable host, and finished turn require different responses. | A scoped report establishes who made a claim. A captured commit, host check, review, delivery record, and product assessment each answer a different question. |
| What survives loss of contact? | Detach leaves the daemon running. A cold restart restores structure and supported conversations in fresh processes. Event history is bounded. | Stored metadata, keyed receipts and finish subscriptions can survive. Provider history can rebuild a projection. An ordinary queued peer prompt can disappear in a crash. | A detached worker survives API loss. Sealed run state, worker journals, pending operations and evidence survive within their retention. | Where is the scale boundary? | Each server owns its local panes. ## Recommendations in adoption order

### 1. Make child progress resumable by a coordinator

Paseo persists who wants the notification and waits for dispatch acknowledgement. Herdr exposes a specific error when the observer has fallen behind the retained history. Infinite already has a mission inbox, work-event outboxes, per-project signals, and a blackboard. **Start with a read-only feed for one mission and its subteams.** Project a compact snapshot and a cursor. When the child changes, wake the observer and let it retrieve the relevant run record, report or check. Work remains on the child host. [Paseo subscription registration](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/server/agent/finish-subscriptions/index.ts#L309-L353) · [Herdr lost-history handling](https://github.com/herdrdev/herdr/blob/e8d7d9705a7a2c89cef4dd42079379f05685af87/src/api/subscriptions.rs#L317-L342) · [Infinite host feed and scheduler](infinite.md#what-limits-unattended-scale-today).

Bind each observation to runner, parent, child run, task or member, and revision. Store a feed generation with its sequence so a restored or rebuilt projection can force a fresh snapshot. An acknowledgement advances a reader's cursor. Subsequent dispatch must still re-read current state, scope, halt, and tracking gates. Keep reconciliation on startup and periodically for lost wakes, expired timers and provider state that emits no event. Define how each trigger handles missed occurrences. A burst of duplicate signals may need one catch-up cycle, while two independent incidents may each need a tracked response. **Exercise the failure cases.** Disconnect during a report, drop a wake, replay a duplicate, cancel the child, and replace an attempt under the same task. Simulate a lost connection to a living worker as well as a confirmed worker exit. Expose the distinction on the feed and require the host to reconcile the old attempt before replacing it. The rebuilt view must match the sealed records, show stale evidence under its original attempt, and cause zero duplicate assignments. Compare catch-up time, state reads, and stale decisions with today's polling.

### 2. Give each planned change a verifiable reason to exist

Infinite already represents objective criteria and their producers. Its task plan stores instructions, paths and dependencies. Its review evidence indexes the run brief. The missing join is a structured reference from a particular planned task to the objective criterion or prerequisite it advances. Today the coordinator can express that relationship in prose. Paseo's separate parent and dependency concepts are a useful model for displaying it. Its file task store can mark a task done without evaluating its acceptance text. Keep the evidence rules in Infinite. [Paseo task model](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/tasks/types.ts#L13-L28) · [Task close](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/tasks/task-store.ts#L289-L306) · [Infinite plan and criterion records](infinite.md#who-owns-each-fact).

For new goal-owned plans, pin the objective version and let the planner name criterion IDs or a dependent task that needs the work. Validate those references before dispatch. On integration, link the actual task, head, and check receipt. Let the evaluator explain remaining criteria and uncertainty. An unmet criterion with no new evidence can trigger bounded discovery or a wait for a specific event. A material change to the definition of success goes to the owner. Keep older and standalone plans readable with “link unavailable.” **Require three outcomes in the pilot.** An obsolete plan cannot satisfy a revised criterion, a failed check survives a favorable worker report, and an unlinked historical item remains explicitly unlinked.

### 3. Enforce cost and review independence before increasing fan-out

Two workers can finish the same number of turns at very different costs. Extend the existing admit/start/release path with an owner-scoped reservation for metered work. Record measured usage, conservative reserved amounts, and unknown usage separately. A retry with the same launch identity reuses its reservation. When the host cannot bound a new metered attempt, hold admission. Reconcile stale reservations against the worker and durable receipt. An admission limit alone cannot cap an already-running provider turn. A hard in-flight ceiling also needs provider or runtime enforcement. [Infinite admission evidence](infinite.md#what-limits-unattended-scale-today).

For automatic delivery, derive the set of contributing families from actual integrated work on the reviewed head, including repairs and fallbacks. Require coverage by an eligible strong reviewer outside each contributing family. One reviewer can cover several families it did not contribute to. A changed head invalidates the approval. **Test simultaneous admissions for the last budget slot.** Only one should proceed. Missing usage must consume a reservation, and an approval from the sole contributing family must leave automatic delivery pending. Retain existing owner-only permission classes, halt and delivery policy throughout.

### 4. Scale the existing single-writer scheduler against measured demand

The current schedulers already serialize competing transitions. On a quiet runner that is a simple recovery strategy. As retained teams grow, every scan still visits them. Measure active and retained runs separately. If scans consume the admission-latency budget, keep a per-project index of ready or due work, wake it on receipts and timers, and rotate among eligible projects. Rebuild that index from sealed records after a restart. Start on one runner. Introduce placement across runners only when measurements show saturation after local changes. [Infinite scheduling loops](infinite.md#what-limits-unattended-scale-today).

For a future multi-runner trial, give one runner ownership of each run revision. Persist a monotonically increasing ownership generation and require it at the side-effect boundary. A lease expiry alone cannot stop an old runner that resumes after a partition. Keep tenant evidence and provider credentials on the authorized runner. The placement service needs availability and scoped opaque work IDs. **Test fairness and ownership together.** Drive a hot project beside a small project, restart during admission, and resume a stale runner after reassignment. Track p95 eligible-to-start delay per project, oldest ready work, checked work per unit of metered cost, and duplicate or stale effects. Establish baselines and target delays from that workload before claiming a capacity improvement.

## When the owner can stay offline

| Situation | Proposed host action | Evidence to retain |
| --- | --- | --- |
| A task has a known next step within approved scope, profiles and budget | Assign or retry within the existing limit. Run the independent check when the result arrives. | Objective version, task, attempt, writer, integrated head, and check result |
| A provider disconnects after accepting a request, or a remote child disappears | Hold that operation and reconcile its stable identity. Continue unrelated eligible work. | Last acknowledged operation, missing evidence, next reconciliation time |
| A check passes but the evidence for an objective is incomplete | Plan a bounded follow-up against the unmet criterion or wait for its named signal. | Criterion ID, producer, supporting evidence, outstanding uncertainty |
| The next action needs broader authority, changes success criteria, or hits a fuse or repeated-failure stop | Persist the reason and route it to the authorized owner. A previously delegated one-shot permission still needs a current request and the host's checks. | Decision and owner scope, or the exact condition required to resume |

The product contract names additional owner decisions for irreversible or external actions. A generated answer to a question is a recommendation until an authorized path acts on it. These distinctions bound unattended operation even when a coordinator can run continuously. [Infinite authority and recovery](infinite.md#follow-a-report-across-a-failure).

## Worked example

An approved standing goal watches for a revert and requires a repository compatibility check to pass. A matching signal wakes one cycle. Its coordinator proposes a repair linked to that criterion, assigns a scoped writer, and names the downstream compatibility task. The writer reports a fix. The parent can now see who reported it. The downstream task becomes eligible when the host integrates the change and its other dependencies are satisfied. A failing compatibility receipt keeps the criterion unmet even if the worker's report says “fixed.”

If the coordinator disconnects at that point, the proposed feed replays the receipt and the new attempt reads it from the host. A routine, reversible repair can proceed within the original delegation and budget. A proposal to weaken compatibility, widen the write scope, or change a production service needs the authority for that decision. A human need not monitor successful intermediate steps. The Linear record can carry execution evidence, a later scan can confirm landing, and only an explicit user assessment can claim the product goal was achieved. This example illustrates the proposed criterion link and feed. The underlying state transitions are traced in the [Infinite study](infinite.md#follow-a-report-across-a-failure).

## Measuring autonomy

Report the share of eligible cycles that reach a checked disposition without a human touch, alongside raw counts of paused, refused, inconclusive and still-running cycles. Break interruptions down by cause and keep the full arrival denominator visible. Otherwise a system can appear more autonomous simply by rejecting hard work. Use cost per independently checked result with usage coverage, intervention rate, duplicate external effects, stale assignment attempts, and reconciliation age. Review delivery, deployment, and owner-assessed impact as separate outcomes. An end-to-end fleet benchmark for Infinite remains open.

## What was verified

At the pinned revisions, 80 Infinite checks passed in the initial study, including the 50-seed crash simulator. The operational follow-up added 27 passing cases. Herdr passed 45 Rust and 13 manifest tests across both passes. Paseo passed 239 tests across eight suites. A separate Infinite probe confirmed that lineup validation and routing admit different writer and reviewer models from the same family. The source notes contain commands and coverage. An independent review traced the main findings back to the pinned implementations. Cross-host production throughput, live-provider recovery, a real merge, and product impact remain open.
