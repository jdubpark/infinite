# Operational findings from the second research pass

**Add confirmed worker loss and ambiguous restart recovery to the first pilot.** A progress feed can show that a child stopped responding. Resuming unattended work also requires the host to establish whether the old worker can still act. At the other end of the workflow, Infinite already admits owner-authorized work from Linear and Slack and follows up on certain GitHub reviews. Building a second intake engine would duplicate those paths.

## Which existing mechanisms shorten the roadmap

- **Start with existing intake.** A configured Linear/Slack intake persists its request before creating a mission. Approved routines and standing goals can wake on cadence or scoped project signals. The signal vocabulary already covers reverts, external commits, observed landings, and owner direction. When enabled, GitHub review feedback binds the owner's qualifying changes request to the delivered PR and head, persists the intent, and applies one steer. A coalesced failed-CI signal bound to the same run, head, and check would add something new. Paseo's 30-second window batches observations by URL after a change has been seen. Its external trigger matching and continuation keys are documented Hub responsibilities. `server.ts:468–473,2237–2244`, `intake.ts:374–412`, `signals/types.ts:1–29`, `review-feedback.ts:132–179`, `team-review-feedback.ts:38–66`. [Paseo PR digest](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/server/agent/change-request-watches/index.ts#L129-L163) · [Hub continuation ownership](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/docs/hub.md#L40-L48).
- **Measure remaining workspace cost.** Full independent Git clones are real. Infinite already removes eligible integrated member copies and settled run workspaces, preserves blocked or uncertain work, and can resume interrupted cleanup. Measure clone bytes, setup time, queue age, and retained bytes by role. Paseo schedules foreground and background Git operations through three priority lanes. Its strict priority leaves fairness to the workload. A small project waiting behind a hot one makes a good benchmark. `team-workspace.ts:390–433`, `team-retention.ts:147–207,290–329`. [Paseo scheduler](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/utils/git-process-scheduler.ts#L99-L132).
- **Require evidence before enabling another privileged provider.** Paseo's shared tool policy names preapproved MCP tools. Each adapter maps that list into its provider's own controls. Infinite's launcher needs its own evidence of tool isolation. A provider can qualify for a restricted coordinator role after a local role-capability test demonstrates that it can report and cannot invoke ambient tools outside that role. Structured message envelopes preserve source labels and escaping. Authorization still belongs in the host's typed channels. `launch.ts:90–112`, `missions.ts:363–370`. [Tool references](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/protocol/src/agent-types.ts#L546-L554) · [Codex adapter](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/server/agent/providers/codex/options.ts#L67-L89) · [OpenCode adapter](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/server/agent/providers/opencode/options.ts#L53-L80) · [Envelope parser](https://github.com/getpaseo/paseo/blob/cf1a5a9e73a6dd3020fb62a6d10281a2193ff2f2/packages/server/src/server/agent/agent-messages/envelope.ts#L87-L123).
- **Drain and fence before increasing fleet size.** Paseo leaves existing terminals with an older worker and sends new terminals to the current worker. Idle cleanup checks the whole agent family, pending interest and the provider's ability to stop. Routed operations intersect grants at the destination and cannot route another hop. These patterns are candidates for upgrade compatibility and tenant-scoped placement. Distributed task ownership and in-flight budgets need separate enforcement. ## Decisions for an implementation proposal

1. **Prioritize proven single-runner recovery cases.** Exercise a reachable worker, a confirmed-dead worker and an unreachable worker separately. Require zero duplicate live writers and an auditable reason for continuing or waiting. Give that distinction to the mission-feed pilot. Keep broader queue and fleet refactors conditional on measured pressure.
2. **Put the ceiling for external triggers in owner-approved host configuration.** A reviewed repository declaration can select a narrower event within that ceiling. Require a source identity, continuation key and current head. A newly encountered trigger or changed authority needs enrollment. Raw PR and webhook text is input data. Only a host receipt or explicitly authorized owner channel can supply direction.
3. **Keep independent writable Git metadata until an isolation benchmark passes.** A read-only snapshot or private copy-on-write clone can be evaluated against today's independent clones. Test isolation of refs, hooks, configuration, uncommitted changes and retained evidence. The target filesystem's reflink behavior and capacity savings remain unmeasured.
4. **Automate drift that the host can prove.** Retry transient tracker errors and revalidate approved code on an eligible moved base. A changed definition of success, expanded authority, or different post-merge tree still needs its proper evidence or approval. Keep routing scores in the host. The product contract explicitly excludes them from agent prompts. `PRODUCT.md:75–85`.

The outside roadmap's week estimates and 100-agent target have no measured workload attached. Baseline queue delay, independent checked results per cost, intervention causes, workspace bytes and duplicate effects on a single tenant before using them as capacity targets.

## Implementation pilot

A same-family approval provides a measurable delivery test. At the baseline, a fixture team passed its configured check, received approval, launched one delivery agent and recorded its simulated merge. With the pilot, the same team reached `ready-for-review` with `reviewer-family-required`, launched zero delivery agents and recorded no merge. A reviewer from an eligible independent family still permits configured automatic delivery. Recovery can carry partial edits across workspaces and revisions, so contribution history has to follow those edits into the new review.

A newly assigned project manager for a goal with a pinned objective now links each task to at least one active criterion in that version. One bounded correction lets the planner repair a bad reference. It can work on a subset of the objective, and criterion satisfaction still comes from its own evidence. In 200 generated dependency graphs, separating the plan validation and ordering code preserved the baseline task order and fields.

The mission pilot sampled a bound coordinator and its subteam through an authenticated viewer CLI, replayed retained observations, and returned a current snapshot after the API restarted. A mission history needs its own identity when the cache evicts and recreates it. Without that identity, an old cursor can accidentally match a new history. Current workers also need to precede stopped writers in a bounded response so that a full work plan cannot hide its active reviewer.

In a separate scheduler fixture the same child first became unreachable, then reported a confirmed process exit with no work report. Two scheduler passes while it was unreachable launched zero replacements. The observer exposed the exit before another scheduler pass. The existing recovery path then recorded `missing-agent-report`, advanced the run to revision 2 and launched one replacement project manager. This measures the interaction between a reader and the scheduler on one host with a controlled worker. An observer losing its connection gave it no authority to replace an assignment.

One hundred concurrent readers of the same mission shared one source read, one worker probe and one cursor. With 100 distinct missions and all worker replies held, the observer started eight probes and returned `not-sampled` for 92 missions. All 92 returned a running observation when queried individually after the replies were released. This in-process workload exercises observer contention and recovery. It measures neither worker execution throughput nor provider cost. The repeatable coalescing and cap tests are in `tests/mission-progress.test.ts`.

The goal-planning simulator exercised 12 scripts and 20 reopen operations. Six corrected plans advanced and six repeated invalid plans stopped. Four more seeds exercised delivery attribution across Git edits and host restarts. The simulators detected six deliberately introduced faults, including losing a spent correction and accepting a different reviewer. Re-run the two groups with `node --import tsx --test --test-name-pattern='seeded team delivery|delivery simulator catches|goal-plan simulator|seeded goal' tests/team-run-sim.test.ts`.

These checks used local provider and repository fixtures. Unobserved worker transitions, irreversible effects from an earlier process, live provider costs and fleet capacity remain outside the measured result. A socket failure alone cannot give a new writer ownership of the old assignment.

## Polling several missions in a fixed order

On November 25, the pilot merged into main at `67a5a94f`. A local client then called the mission progress HTTP endpoint 64 times. It polled eight missions in the same order for eight rounds, allowing each response to finish before starting the next. Each mission had one coordinator and two child teams with four running workers each. Fixture sessions supplied the worker states.

The endpoint directly observed 56 of the 64 child workers. It missed the same worker in each mission on all eight rounds. One host-wide counter rotated the candidates for every read. Eight intervening steps returned the next read of each mission to its original position among eight candidates. The eight-probe host cap left seven places for children after the coordinator took one.

With the sampling position stored in each mission's bounded history, the same requests observed all 64 workers. The position advances past the children whose probes were admitted. In a second fixture with 16 child workers on one mission, three reads reached 16 distinct workers, up from nine. Both workloads peaked at eight concurrent worker reads before and after the fix.

When another mission occupied all eight slots, the endpoint returned `not-sampled` for every child. Across 56 such pages interleaved with eight reads at available capacity, all eight children were eventually observed. An authenticated viewer CLI on a disposable host also resumed child progress and recovered its current snapshot after an API restart. The multi-mission regression runs with `node --import tsx --test tests/mission-progress.test.ts`. These results measure worker visibility on one host.
