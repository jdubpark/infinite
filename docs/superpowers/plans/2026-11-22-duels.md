# Slice 1: judge and calibration

## Header

**Goal.** Tell the owner how well a judge model picks the better of two diffs. The owner names a judge profile in `teams.lineup.judge` and asks for a calibration. The host judges pairs of past dev-set trials, one resolved and one not, under the eval identity, with the labels swapped. It stores the accuracy, its Wilson lower bound, the swap agreement, and a state of `ok` or `not-ok`.

**Architecture.** A judge is the one member of a judge run. A judge run is a replay run (`run.replay`) with purpose `duel`. `TeamService.createForReplay` creates it and `TeamReplay` drives it. The trial pump runs judgements as a second kind of live work beside trials, so the eval identity still runs one session at a time. A new evidence module stores calibrations and judgements. Two routes and three CLI commands let the owner start a calibration, cancel it, and read it back.

**Off by default.** Nothing in this slice runs unless `teams.lineup.judge` is set and the owner posts a calibration.

**Tech.** TypeScript, zod 4, `node:test`, and the evidence store (SQLite with sealed payloads and blind indexes).

## Rulings

1. **Judge shape.** A judge is a `judge` member inside a judge run. A judge run holds one judge, no tasks, and never a replacement. In phase 1 only the calibration job creates one. Phase 2 reuses the run, the prompt, the package writer, and the report. It adds the duel caller (a package from the contestants' captured commits and the production run's steering and answers), `task.duel`, the tie-break, the `duels` table, and an identity rule apart from purpose (Ruling 6).
2. **Judge run input.** `createForReplay` takes `ReplayCreate | JudgeCreate`. The seed puts the judge profile, without `limitFallback`, in every lineup slot. It has no tasks, status `implementing`, and the title and objective "Judgement". `created` emits only `run.created` with `{ projectId, purpose: "duel", trialId }`. It emits no `plan.accepted` and no `task.planned`.
3. **Judge steps.** `TeamReplay.judgeStep(stored)` returns true for every run whose `run.replay.purpose` is `duel`. The service therefore never starts a project manager in a judge run. It prepares the judge only when the run has no member at all and no ending.
4. **Judge context.** The context file is `{ kind: "judge-context", runId, revision, baseCommit, duelId, steering, ownerAnswers, package: ".git/infinite-judge" }`. It omits `assignment`. The report binding stays in the `INFINITE_TEAM_ASSIGNMENT` environment variable, as for every member. It names the judge itself, never a contestant.
5. **Accepting a judgement.** The host accepts a judgement when `assertMemberReadOnly` passes (through the replay host's `operation`), `duelId` equals the run's `replay.trialId`, and it arrives within `judgeMinutes` of `memberStartedAt`. Otherwise the run ends `changed`, `mismatch`, or `timeout`. A `question` or `blocked` report ends the run with that name. An accepted judgement sets `replay.ending = "judged"` and `replay.judgement = { preferred, rubric }`. The summary stays in the run record only, as Part 5 of the design says.
6. **Session identity.** `"duel"` joins `LEARNING_PURPOSES` in `types.ts`. A judge session then gets the eval agent profile, `_eval` egress, Code Mode off, and no injected context. It is hidden from session lists, the notifier, and the decision queue, like a trial. Nothing creates a `duel` session today, so nothing changes without a judge. Phase 2 must split this rule, because its challenger has purpose `duel` but is a production member (disagreement D3). Task 7 writes that constraint as a comment on `LEARNING_PURPOSES`, so the next reader meets it in the code.
7. **Outcome records.** `run.created` with purpose `duel` sets the run summary's source to `duel`. The projector writes no outcome row and no member-result row for a `duel` run. A judged preference is a model's claim. It lives only in `judge_judgements`, never in an outcome, a member result, a scorecard, or a router input.
8. **Lineup slot.** `teamLineupSchema` gains `judge: teamModelProfileSchema.optional()` after `evaluators`. It becomes the new last key, and the "Keep this last" comment moves above it. The judge is not in `lineupProfiles`, so createRun's provider checks, routing, trial candidates, and fallback chains do not see it. `superRefine` refuses a judge `limitFallback`. A judge id must name the same identity wherever that id appears in the lineup. There is no tier rule: calibration measures fitness.
9. **Role and report.** `TeamRole` gains `judge`. `teamReportVariants` gains `judgementReportSchema`, the design's schema exactly. `scores` is the four dimensions of rubric version 1 (`correctness`, `cleanliness`, `extensibility`, `docs`), each an integer from 1 to 5. *(My call: the reviewer's rubric carries a `why` per dimension. The judge's summary carries its reasons.)* The judge accepts `judgement`, `question`, and `blocked`.
10. **Prompt.** `judgePrompt(provider)` takes no profile and no run. It holds the four rules of Part 5, the package paths, and the report fields. It adds Codex sandbox and member tool text for Codex, `contextAccessInstructions()`, `readOnlyWorkspaceInstructions`, and `reportingInstructions(provider)`. It never calls `profileInstructions`. `judgePromptVersion(provider)` is `promptVersion("judge", provider, undefined, false)`. It is the same for every judge profile of one provider.
11. **Package.** Four files in the workspace's Git metadata directory, under `infinite-judge/`: `A.patch`, `B.patch`, `task.json`, and `gate.json`. A patch is the stored trial patch, a `git diff --binary` tree diff with no author, date, or message. `task.json` holds exactly `title`, `instructions`, `paths`, and `acceptance` (the brief's criteria, or `[]`). `gate.json` holds exactly `A` and `B`, each `{ scope, checks }`. Calibration writes `{ scope: "pass", checks: "skipped" }` for both, because only graded trials pair. The package never holds a profile ID or label, provider, model, member, session, trial, or task ID, grade, resolved flag, report summary, usage, or timing. The pump writes it through the eval launcher's `exec` op, after the workspace is ready and before the judge run starts. The launcher's `clean` op removes it with the workspace.
12. **Label order.** `labelDraw(seed)` is the low bit of the first byte of `sha256(seed)`. A calibration seed is `${calibrationId}:${pairIndex}`. Ordering 0 puts the resolved trial in A when the draw is 0. Ordering 1 swaps the labels. Phase 2 seeds with the duel ID.
13. **Calibration job.** Kind `calibrate`. It is owner-created, finite, and expiring, like a replay job, but it lives in its own tables, not `eval_jobs`. The request is `{ requestId, judgeProfileId, pairs?, projects?, judgeMinutes?, expiresAt? }`. `pairs` is 30 to 60 (default 36). *(Coordinator ruling: the state needs 30 counted pairs, so a request for exactly 30 fails on its first dropped pair. The default leaves six spare.)* `projects` is 1 to 20 project IDs (default: every project whose team settings hold an `eval` block). `judgeMinutes` is 2 to 30 (default 10). `expiresAt` defaults to, and is at most, `JOB_EXPIRY_DAYS_MAX` (30) days ahead. The refusals are `judge-not-configured`, `judge-profile-mismatch`, `judge-launch-missing`, `calibration-active`, `request-conflict`, `eval-config-incomplete`, and `too-few-pairs`.
14. **Pair selection.** At creation the job reads pairs through `calibrationPairs`, which gives dev-set tasks only and at most one pair per task. It goes round-robin over the projects in ID order, a page of up to 20 at a time. It skips a pair when either trial's recorded profile has the judge's provider and model (condition 5 of Part 1). It keeps up to `pairs` pairs and then orders them by project, so the pairs of one project run together (Task 9, as built). With fewer than 30 it refuses `too-few-pairs` and stores nothing. The sealed payload stores the pair list and the per-project counts. The read marks every returned group exposed. That is harmless, because a dev group never moves to the holdout.
15. **Scoring.** The unit is the pair. A pair is correct only when both orderings prefer the resolved trial. A tie is incorrect. `accuracy = correct / counted`. Swap agreement is the share of counted pairs whose two orderings prefer the same trial. The lower bound is Wilson at z = 1.96, clamped at 0. The state is `ok` when `counted >= 30` and `lowerBound >= 0.60`.
16. **Failures and retries.** A void ending (`void-limit`, `void-host`, `void-owner`) retries the ordering at most twice. After that the pair is dropped at once, and its other ordering does not start. Every other non-judged ending makes the pair incorrect. A pair is also dropped when a patch has expired, the source skips, or the judge workspace is not `isolated`. A dropped pair is not counted. A calibration completes early, `not-ok` with reason `pairs-dropped`, as soon as fewer than 30 pairs can still be counted, so it stops spending on a result that cannot be `ok`. *(My call: a judge that cannot answer is a judge failure. A host failure is not.)*
17. **Budget.** The learning budget and duel cap do not exist yet (D4). Until they do, the owner's request is the budget: one calibration starts at most `2 x pairs x 3` judge sessions (two orderings, at most three attempts each), each at most `judgeMinutes` long, and it expires. A judge session does not count against a project's `trialsPerDay`, and a trial does not count against a calibration. *(Coordinator ruling: a shared daily cap would let 60 judge sessions starve trials for days, or the reverse. Trials and judgements take turns instead, Task 10.)* When the learning budget is built, calibration moves under its duel cap.
18. **Scheduling gates.** A judgement starts only when all of these hold: the identity is ready, the grader is ready, host load is not held, the project is not halted, the judge's provider is not limited, the free-slot rule for trials holds, no trial or judgement is live, the job has not expired, and the pins still hold.
19. **Pins.** At creation the job pins the judge's identity key (`profileIdentityKey(trialProfileKey(judge))`), its profile epoch (`epochAt`), and `judgePromptVersion(provider)`. If any of them changes before the job completes, the job is cancelled with reason `identity-changed`, and no state is stored.
20. **Validity and the in-force read.** A completed calibration is valid for 60 days from completion (`valid_until`). `calibrationInForce` returns the newest completed `ok` row with the same identity key, the current epoch, the current prompt version, and `valid_until` in the future. Otherwise it returns undefined. `judgeWeight(accuracy) = max(0, 2 x accuracy - 1)`. Phase 2 uses it at admission.
21. **Read-back.** `GET /api/duels/judges` (owner, controller, viewer) lists calibration views, newest first, at most 20. `POST /api/duels/judges/calibrations` and `POST /api/duels/judges/calibrations/:id/cancel` are for the owner only. *(My call: the design names no cancel route, but a finite job needs a way to stop.)* A view carries the profile ID, epoch, prompt version, status, reason, state, pair counts, correct, accuracy, lower bound, swap agreement, per-project pair counts, `judgeMinutes`, cost, times, and `inForce`. It never carries a task, trial, patch, model text, or judge summary. The CLI commands are `infinite duels calibrate`, `infinite duels judges`, and `infinite duels cancel`.
22. **Isolation filter.** Both statements of the calibration read admit only `isolation = 'isolated'` trials (D1).
23. **Cost.** The pump's sweep reads the judge session's cost before it removes the session, as for trials, and stores it on the judgement row. The view sums it. The close of a judgement reads no cost: the store keeps the first cost it is given, and the usage ledger may not hold the session yet.
24. **Off state.** With no `lineup.judge` and no calibration: the parsed lineup has no `judge` key, every existing prompt pin holds, the pump never takes a judgement turn, the routes answer from empty tables, and no row is written anywhere.
25. **Launchers and migrations.** No launcher form changes: the pump uses the existing `exec` and `clean` ops. The new module creates two new tables. No existing table changes.
26. **Baseline files.** The hooks in `teams.ts` are listed in Task 1 and Task 7. `goals.ts` and `server.ts` are not touched: the routes register inside `EvalHost.routes`. An edit stays on its line only when the line is still one statement that reads well: a value added to a list or a record, or one more term in a condition. Never join statements, and never grow an object literal on one line to save a line. When a hook needs a line, add the line and raise that file's baseline entry by hand, by exactly the lines added, in the same commit, with the reason in the commit message. Never run the size script with `--update`.

## Where the design and the code disagree

- **D1.** Part 9 counts a pair only when both trials are `isolated`. `eval-calibration.ts` does not filter on isolation. Ruling 22 adds the filter.
- **D2.** Part 5 says the context file holds no member ID. Every context file carries `assignment` (with `memberId`), and the report binding carries it in the session environment. Ruling 4 omits it from the context file and keeps the binding.
- **D3.** The design gives the challenger and the judge the same purpose, `duel`. The code ties the eval identity to `learningPurpose`, and `LEARNING_PURPOSES` lacks `duel`. Phase 1 adds it (Ruling 6). Phase 2 must split identity from purpose.
- **D4.** Part 8 spends calibration sessions from the duel cap of the learning budget. The code has no learning budget, `reserve`, or measured medians. Ruling 17 makes the owner's request the bound.
- **D5.** Part 5 says the judge's session exposes only the `report` tool. The eval agent profile gives the judge its normal read and shell tools. Phase 1 gives no entry tools or host-profile tools, and `assertMemberReadOnly` enforces no change.
- **D6.** Acceptance 4 forbids a provider name in the prompt. The shared reporting and Codex sandbox text name the judge's own tool surface. Ruling 10 keeps that text, and the test forbids any other provider's name.

## Owner approvals before use

1. **Host configuration key.** Set `teams.lineup.judge` to a profile. Approvals that pin the lineup fingerprint change only once it is set.
2. **Account.** An eval-identity login for the judge's provider, configured as `eval.member.agents[provider]`. Without it, `create` refuses `judge-launch-missing`.
3. **Egress.** The `_eval` allow list must hold the judge provider's API host, if it does not already.
4. **Spend.** Each calibration request authorizes at most `2 x pairs x 3` judge sessions of at most `judgeMinutes` each (216 sessions for the default 36 pairs). They do not count against `trialsPerDay`. The duel cap of the design arrives with the learning budget.
5. **No launcher change.** The pump uses the existing `exec` and `clean` ops. Nothing installs or changes a launcher.
6. **No migration of existing data.** The new module creates `judge_calibrations` and `judge_judgements` on first open.

## Decided questions (coordinator, 2026-11-22)

- **Q1. A judge that does not answer.** A timeout, a question, a blocked report, or no report counts the pair as incorrect (Ruling 16). A judge that cannot answer is not a reliable judge. Only a host or limit failure is retried and then dropped.
- **Q2. Pairs from the judge's own model.** Skipped (Ruling 14). Part 1, condition 5 requires a judge that differs from both contestants, and calibration measures the judge under that same condition.
- **Q3. The cap.** The owner's request bounds the spend (Ruling 17). No new configuration key, and no shared count with `trialsPerDay`.
- **Q4. The judge's own provider in its prompt.** Allowed (D6). Acceptance 4 protects the judge from learning which profile wrote which patch. The reporting and sandbox text name only the judge's own tool surface and are the same whatever the contestants are. The test forbids every profile ID and label, every member, session, and trial ID, and any other provider's name.
