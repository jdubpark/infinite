# Workspace sync

Workspace sync keeps a cloud project directory current with the owner's laptop checkout. It is one way, laptop to cloud, and it applies only to projects in `laptop` source mode. A project in `github` mode is updated by the host from GitHub instead, as described in [Source modes](#source-modes). The cloud directory is the executing copy for every cloud session in that project. Changes made there travel back only through `infinite pull`, into a new directory. Command usage is in the [CLI guide](cli.md#workspace-sync-and-pull).

## Source modes

Each enrolled project has one source mode. In `laptop` mode, the project's code comes from the owner's laptop through workspace sync, which this page describes. In `github` mode, the host follows the project's base branch on GitHub. It fetches that branch and fast-forwards the project directory itself, with no laptop process running. The two modes never apply to one project at the same time, so a laptop upload cannot report `cloud-changed` against a tree the host moved.

`infinite repo init` records `github` when `origin` is an HTTPS or SSH `github.com` URL without embedded credentials, and `laptop` otherwise. `--source laptop` keeps workspace sync for a GitHub checkout. `--source github` switches an enrolled project to GitHub mode, stops any laptop sync service recorded for it, and reads the followed branch from `origin/HEAD`, else local `main` or `master`. Projects enrolled before this mode existed stay in `laptop` mode until they are enrolled again.

While a project is in `github` mode, every laptop sync route for it answers `409` with code `source-github`, and its message names `--source laptop`. `infinite sync` in such a checkout prints that the project follows GitHub and starts no service. The pending reasons on this page apply only to `laptop` mode. GitHub mode reports its own state, described in [GitHub-tracked sources](teams.md#github-tracked-sources).

## Folder mapping

A native CLI launch without `--project` selects the invoking checkout, starts or reuses its detached sync service, and waits for the first applied generation before creating the session. The Git root defines the sync scope; outside Git, the current directory defines it. The session retains the launch directory within that root.

Paths below the local home are preserved below the server home: `LOCAL_HOME/Projects/sample/apps/web` becomes `SERVER_HOME/Projects/sample/apps/web`, with spelling and case unchanged. The full home-relative root determines project identity, so `Projects/sample` and `Work/sample` remain separate. Mappings are sealed in private host state and restored after API restarts. Web and phone clients can select these projects from the ordinary project list.

The server home defaults to the API account's home directory. Operators can set the absolute `sync.homeDir` in private host configuration to the intended server workspace home. When agents use a separate Unix account, provision that directory on encrypted storage with shared group traversal and default ACLs as described below; keep private provider and control homes separate. `sync.sharedGroup: true` makes applied trees group-writable. Changing `sync.homeDir` relocates the mapping root and requires an explicit workspace migration before reusing existing sessions.

Only a paired owner CLI on a single-tenant host can resolve a folder with `POST /api/projects/resolve`, using `{ "path": "Projects/sample" }`. `/api/me` advertises `capabilities.workspaceMirror: 1`, and `mirrorForget: 1` when mappings can be forgotten. New project IDs use a readable slug of the final home-relative path component, prefixed by its parent for paths with at least three components; a short path hash disambiguates collisions. IDs are stored with their paths in sealed host state and are never reissued to another folder. Older path-array state keeps its existing `folder-` IDs. The host creates the directory and returns its project `id`, `name`, and server `path`. Absolute paths, traversal, hidden top-level directories, symlink aliases, protected host state, and projects or team [teamwork folders](teams.md#configuration) that overlap it are refused. Local folders outside home require an explicit configured `--project`; an older host also requires `--project` until upgraded. The client never falls back to the pairing's default project when automatic mapping fails.

`infinite projects forget [DIRECTORY] [--project ID]` forgets a mirrored mapping without deleting its server directory or cloud files. Without `--project`, it matches the current directory (or supplied directory) by its Git root, relative to the local home. A forgotten ID stays reserved for that folder and is reused if the same folder is resolved again. Forgetting is refused while a session, sync apply, file or repository change, or handoff holds the project, while a team for it is not `ready-for-review`, `no-change`, or `cancelled`, or while a goal for it is running, waiting for input, or paused. Team enrollment, sync records, and cloud files remain on the server, so mapping the same folder again restores its earlier settings immediately. With `sync.sharedGroup`, forgetting changes a real project directory to mode `2750`, removing group write from the folder itself. This stops agents from creating, renaming, or removing entries directly in that folder; files and subfolders inside keep their existing modes. Resolving that same forgotten folder restores mode `2770` and reapplies its saved team enrollment. The CLI also removes its local repository bindings for that ID. Use it to restructure a folder, for example to map `Projects/sample/codebase` after `Projects/sample` had been mapped as a whole.

`--project ID` explicitly selects an existing server project and does not start automatic sync. `--laptop` retains its existing executor and handoff behavior. A first sync that meets preexisting cloud files stays pending and blocks the automatic launch; the owner must reconcile and apply it. Later pending generations retain the running-session and cloud-change rules below.

## Laptop side

`infinite sync --project ID`, run inside a checkout, starts a detached service for the Git root of the current directory, or for the directory itself outside a Git repository. The service captures the tree with the same scanner the `--laptop` mode uses: bounded SHA-256 chunks, stable reads, and metadata verification. Scope and capture rules are those of [project scope and checkpoints](hybrid-execution.md#project-scope-and-checkpoints), with exactly one root, so the root's own `.git` directory travels too. When the root is a linked Git worktree, the upload also includes Git metadata from outside the root. From the common repository it takes objects, refs, ref logs, packed refs, `info/`, `shallow`, `description`, and a projected `config`. From the worktree's own metadata directory it takes `HEAD`, `index`, the worktree's ref logs and refs, in-progress merge, rebase, cherry-pick, revert, and bisect state, and a projected `config.worktree`. A Git config can carry credentials, such as a token in a remote URL or an `http.extraheader`. Without `--project`, `infinite sync` uses the same home-relative mapping as a native launch.

On macOS, captures follow file changes with a quiet capture at least once every 10 minutes; other platforms rescan every 3 seconds. Among captures that run, full reads are at most once a minute. The service uploads only when content, layout, or modes changed. Each upload begins a generation, asks the host which chunks it lacks with `POST /api/projects/:id/sync/has`, sends those with `PUT /api/projects/:id/sync/blob/:hash`, then commits the manifest. `infinite sync` returns after the first commit. The service reports progress while it captures, uploads, and waits for the host to apply that commit, so a first upload of a large tree can take many minutes. Startup fails only if the service reports nothing for 60 seconds or keeps failing before its first commit; chunks already uploaded stay on both sides, so running `infinite sync` again resumes. A commit request may wait up to 30 minutes for the host's apply.

Sockets, FIFOs, and device files, such as Git's fsmonitor socket or a language server's socket, have no content to copy, so captures leave them out. `infinite sync` prints the ones its first capture left out, once, and `--status` shows how many the latest capture left out.

It records its pid, root, and last commit beside the private client configuration under `sync/`, next to its local chunk store; both must lie outside the synced checkout. Closing the terminal leaves it running. It does not restart after a reboot; run `infinite sync` again. One service runs per project. Automatic mapping reuses a running service for the same root and host; an explicit `sync --project ID` refuses a second start until the first is stopped.

`infinite sync --stop` signals the recorded pid only after confirming that the process still runs as the sync service, then removes the record. `infinite sync --status` lists each project's local service and, when the host answers, its sync state. Both work without reaching the host. A record whose process is gone, after a crash or reboot, is reported as stale.

Failures are retried, and `--status` shows the current problem. After a failed commit, the next attempt waits twice as long as the last one, from 3 seconds up to 5 minutes, until a commit succeeds. When the host keeps a generation but cannot apply it for a reason the same content would meet again (`apply-failed` with category `permission`, `cross-device`, `special-file`, or `missing-path`), the service rechecks that held apply every 30 seconds and does not push that content again. It pushes the next laptop change, and it clears its problem once an explicit apply or a reset on the host replaces the failure marker. A host refusal with 401, 403, 404, or 413, such as a revoked device key, a removed project, or a manifest over the host's bound, stops the service. It starts through an owner CLI launch or an explicit `infinite sync` command.

## Host side

The host stores received chunks and the newest manifest for each project under its private state directory. Manifest and apply records are sealed with the host key. Chunks are plaintext files and need [encrypted host storage](security.md#required-on-a-real-host). Upload and export routes accept only a paired owner bearer key; a browser session is refused. On a host that is not single-tenant, such as a tenant-development runner, every sync route answers `403`, as laptop execution does.

The host verifies each chunk against its hash and accepts chunk bodies up to the 256 KiB chunk bound; a larger body answers `413`. Presence checks take at most 512 hashes. A commit is parsed after owner authentication, with a JSON limit of the 32 MiB manifest bound plus 64 KiB for the generation that wraps it. It is refused when a newer generation has begun, when the manifest has more or fewer than one root, or when it names a chunk the host does not have.

The host's scans of the cloud tree also leave special files out, so a stale dev-server socket neither blocks a scan nor counts as a cloud change. `skipped` in the sync status counts the special files the latest host scan left out since the API started.

A committed manifest is **applied** when no cloud session is running or starting in that project and the live cloud tree still matches the scan the host took right after the last apply. The comparison ignores the Infinite-owned `.infinite/` directory. Before the first apply, the directory must be empty apart from `.infinite/`. A manifest whose entries equal the applied generation is recorded as applied without replacing the tree.

Applying materializes the tree in a sibling stage directory, moves the current directory to `.NAME.infinite-previous` (replacing the older copy), and renames the stage into place. The cloud project's `.infinite/` directory moves into the new tree. A `.infinite/` directory from the laptop is discarded, so the cloud copy wins. If a step fails, the live tree and its `.infinite/` directory are moved back and the generation stays pending with reason `apply-failed`. The parent directory is synced after the renames. When the host stops in the middle of an apply, the next API start and the next apply finish the job: a missing project directory is restored from `.NAME.infinite-previous`, a `.infinite/` directory left in a stage moves back into the project, and leftover `.NAME.infinite-stage-*` directories are removed. A stop after the new tree is in place but before the apply is recorded leaves the new tree live; the next laptop change then reports `cloud-changed`, and `infinite sync --apply --force` records it. Without `--force`, the drift check has just verified the live tree, so files unchanged since the applied generation become hard links into it instead of being rewritten. The previous copy therefore shares those files with the new tree, and an in-place edit of one changes both. A forced apply writes every file. The stage is flushed to disk once before the swap. The reference for the next drift check is taken from the staged tree just before the swap: the file content the manifest names plus each entry's mode, link target, and stat stamp. If that metadata pass cannot describe the stage, the host scans the new tree instead. An apply still walks the whole tree for the drift check and the stage, so its time grows with the project, but only changed files are written. The host refuses a project path that is the filesystem root, the host account's home directory, or a directory holding the host's own state.

When cloud agents run under a different Unix account from the host, as in the [Ubuntu template](../deploy/ubuntu/README.md#separate-identities-and-directories), the applied tree must be writable by the agent and every file the agent creates must stay readable and removable by the host. The host materializes for a shared group when the project directory's parent has the setgid bit or the config sets `sync.sharedGroup: true`: directories 2770, files group read/write, and group execute where the laptop file is executable. Otherwise files keep the laptop's modes. A default ACL granting the group `rwx` must sit on that parent, because each apply renames a tree staged beside the project directory into place and new directories inherit the parent's default ACL. Without it, files an agent creates under `umask 077` block drift scans and the next apply. `.infinite/` must stay writable by the host, which moves it into each new tree. The agent account also needs a scoped Git `safe.directory` entry, since the host owns the repository.

While a commit or apply holds a project, `POST /api/sessions` and `POST /api/sessions/:id/resume` for that project answer `409` with code `sync-applying`. This covers Infinite-managed and cmux sessions. A session admitted just before is counted as starting, so the apply sees it. The running check reads the same session list the clients show, cmux sessions included. A session counts while it is starting or running. It also counts while its worker does not answer and the recorded worker or provider process still lives; such a session reads `unavailable` or `recording-error`. An exited session never counts. A pid that the system reused for another process keeps the apply waiting until that process ends. If the session list cannot be read, the project counts as running. `--laptop` sessions do not block an apply, because their tools run against the laptop or a prepared checkpoint rather than the project directory. Records written before the execution location existed count as laptop sessions when they carry a hybrid workspace.

A manifest that cannot be applied stays **pending** with a reason. The pending marker always describes the newest received generation.

| Reason | Meaning | What clears it |
| --- | --- | --- |
| `session-running` | A cloud session is running or starting in this project | After it exits: `infinite sync --apply`, **Apply now** on web or phone, or the next laptop change |
| `awaiting-apply` | Reported in place of `session-running` once no session holds the project; never stored | `infinite sync --apply`, **Apply now** on web or phone, or the next laptop change |
| `cloud-changed` | The cloud tree differs from the scan taken after the last apply, or the directory was not empty before the first apply | `infinite pull` to save the cloud copy, then `infinite sync --apply --force` or **Replace cloud files** on web or phone |
| `apply-failed` | The drift scan or the swap failed; `category` and `message` say why | Fix the cause, then `infinite sync --apply`, **Apply now** on web or phone, or the next laptop change |

An `apply-failed` marker carries a `category` and a fixed `message` that never names a host path:

| Category | Typical cause |
| --- | --- |
| `permission` | The host account cannot read, write, or remove part of the tree, such as an agent-created file without group access |
| `cross-device` | The project directory is a mount point or spans filesystems, so it cannot be renamed |
| `no-space` | The host ran out of disk space or quota |
| `special-file` | A device or FIFO stood where the host expected a regular file |
| `missing-path` | The project directory is missing and no previous copy could restore it |
| `other` | Anything else, such as the cloud tree changing during the scan |

`--force` skips the drift check and the identical-manifest shortcut; a running session still refuses the apply. A forced apply therefore replaces the tree even when the manifest matches the applied generation, which resets cloud edits to the laptop content. An explicit apply that is refused answers `409` with the reason as its code and leaves the generation pending. A failed apply answers `409` with code `apply-failed`, its `category`, and the message in `error` and `message`. Any other failure on a sync route answers `409` with code `sync-failed` and a category, never the session refusal text.

`GET /api/projects/:id` returns the project's `id`, `name`, and a `sync` object. `lastSyncedAt` and `lastSyncedManifest` describe the newest received generation, `appliedAt` and `appliedManifest` the generation in place, and `pendingGeneration` (`id`, `capturedAt`, `receivedAt`, `reason`, and for `apply-failed` also `category` and `message`) a waiting one. Any paired role can read it. `infinite projects` and `infinite sync --status` print a summary of it: sync age, apply age, and the pending reason. Before a cloud launch, the CLI reads it and prints `Laptop changes from AGE are pending; run infinite sync --apply` when a generation waits, then starts the session on the tree in place.

## Clients

On a cloud host, the web and phone Create screens show the selected project's sync age, apply age, and pending reason. Owners get **Apply now** for `session-running` and `apply-failed`, and **Replace cloud files** for `cloud-changed`; the second asks for confirmation first. An `apply-failed` line shows its category and message. On the web, the sync line is not a live region, since its ages change on every poll; screen readers hear only a new pending reason or an applied generation. Laptop hosts hide sync state. The session view shows "Tools run on" the machine, or "your laptop" for `--laptop` execution, using the live executor location when the session reports one.

## Pull

`infinite pull` asks the host to scan the live cloud project tree, downloads the chunks the laptop lacks, materializes the tree into a new directory, and prints its path. Without `--output` the directory goes into private client storage. An existing destination is refused, and so is one inside any checkout a sync service on this laptop has recorded, running or not, because the service would upload the pulled copy. The checkout is never written. The copy includes `.infinite/`. Compare and merge by hand. `infinite recover SESSION_ID` remains the download for `--laptop` sessions after handoff.

## Limits

One root per project; `--include` belongs to `--laptop` execution. No merge: a forced apply replaces the cloud tree, and only one previous copy is kept; after an ordinary apply it shares unchanged files with the live tree, so it is a rollback aid rather than a backup. No two-way sync. Process memory, databases in use, and files outside the root are not covered, apart from a linked worktree's Git metadata listed above. Chunk stores on the laptop and the host grow without automatic pruning. The single-tenant trust boundary applies: everything in the checkout, and for a linked worktree the Git metadata listed above, travels to the host, including any credentials stored there.
